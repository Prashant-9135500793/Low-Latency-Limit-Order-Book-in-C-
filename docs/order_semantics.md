# Order Semantics and Execution Reports

## Order fields

`Order` remains fixed-size, standard-layout, trivially copyable, and pointer-free so it can travel through the shared-memory protocol and fixed-capacity queues.

```cpp
struct Order {
    uint64_t id;
    Side side;                 // BUY or SELL
    OrderType type;            // LIMIT or MARKET
    TimeInForce time_in_force; // GTC, IOC, FOK
    OrderFlags flags;          // POST_ONLY or NONE
    int64_t price;             // integer ticks; ignored for MARKET
    uint32_t quantity;
    uint64_t sequence;         // assigned by the engine
};
```

## Semantics matrix

| Type | TIF/flag | Behavior |
|---|---|---|
| LIMIT | GTC | Match at acceptable resting prices, then rest any remainder |
| LIMIT | IOC | Match immediately and expire the remainder |
| LIMIT | FOK | Fill the full quantity immediately or reject before mutation |
| MARKET | IOC | Sweep available opposite liquidity and expire the remainder |
| MARKET | FOK | Fill fully against available liquidity or reject before mutation |
| LIMIT | GTC + POST_ONLY | Rest only when it would not trade immediately; otherwise reject |

A market GTC order is invalid because it has no price at which an unfilled remainder could rest. Post-only is restricted to GTC limit orders.

## Validation order

`MatchingEngine::processOrder` performs the following stages:

1. allocate a command sequence;
2. validate ID, enum values, flags, quantity, and type/TIF combinations;
3. reject a previously accepted client order ID;
4. calculate immediately executable quantity;
5. apply pre-trade risk policy;
6. enforce post-only and FOK preconditions;
7. consume the client ID and match under price-time priority;
8. rest an eligible GTC limit remainder;
9. return an execution report and append generated trades to the caller's vector.

Rejected IDs are not consumed, allowing a client to correct a malformed command and retry. Once a command is accepted, its ID is consumed even when an IOC expires with no fill. This avoids two logically different accepted commands sharing one audit identity.

## Execution report statuses

- `REJECTED`: no book mutation; `reject_reason` explains why.
- `RESTING`: accepted with zero immediate fill and a live remainder in the book.
- `PARTIALLY_FILLED`: some quantity executed; either a GTC remainder rested or an IOC/market remainder expired.
- `FILLED`: the requested quantity fully executed.
- `EXPIRED`: accepted but no quantity executed and no remainder rested.
- `CANCELED`: a live resting order was removed.

For new orders:

```text
requested_quantity = executed_quantity + remaining_quantity
trade_count         = number of Trade records generated by this command
```

For a successful cancel, `requested_quantity` carries the removed resting quantity and `remaining_quantity` is zero.

## Risk checks

`RiskManager` is deterministic and synchronous. Configurable limits are:

- maximum order quantity;
- minimum/maximum limit price;
- maximum price × quantity notional, checked without integer overflow;
- maximum number of active resting orders;
- an atomic kill switch.

The active-order cap is applied only when a command can add a resting order. A fully crossing GTC command may still execute while the active-order cap is reached because it cannot increase the live-order count.

## FOK atomicity

FOK uses `OrderBook::executableQuantity` to walk acceptable opposite price levels without changing them. Matching begins only when the complete requested quantity is available. Therefore an unfillable FOK leaves quantities, FIFO order, best prices, depth, and the active-order index unchanged.
